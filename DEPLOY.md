# Деплой «Вместе» backend — Supabase + Render (без карты нигде)

## Итог за 30 секунд

- Бэкенд переехал с локального SQLite на **Postgres** — конкретно на бесплатный
  проект **Supabase** (постоянный тариф, без карты, только «засыпает» после
  7 дней полного бездействия и просыпается сам по первому запросу).
- Из-за этого **проблема с эфемерным диском на Render больше не актуальна** —
  раньше это было главным препятствием, теперь данные живут отдельно от
  сервера. Render free становится полноценным постоянным домом, а не только
  демо-стендом.
- Код проверен целиком: `npm install`, миграция на чистой базе, `./test.sh` —
  всё проходит без ошибок на реальном Postgres (не на предположениях).
- Карта не нужна нигде в этой связке: ни у Supabase, ни у Render free.

---

## Почему Supabase, а не Northflank или VPS напрямую

Все три упирались в разные стены:

- **Render free** (compute) без изменений в коде хранить данные не может —
  диск эфемерный, база сбрасывалась бы при каждом уходе в сон.
- **Northflank** даёт собственную бесплатную базу, но карту привязать нужно
  всем и на любом тарифе, а РФ-карты такие проверки часто не проходят.
- **VPS** решает всё, но стоит денег, которых пока нет.

Supabase закрывает именно ту дыру, которая была у Render (реальный Postgres
вместо локального диска), и при этом не требует карты вообще. Место, где
реально крутится Express-сервер, при этом остаётся любым — можно на Render,
можно позже перенести на Northflank или VPS, ничего в коде менять не придётся:
и там, и там нужен всего один `DATABASE_URL`.

## Шаг 1 — завести бесплатный Postgres на Supabase

1. [supabase.com](https://supabase.com) → Sign up (можно через GitHub) → **New project**
2. Задайте пароль базы (сохраните его — понадобится в строке подключения) и,
   если предложат выбрать регион, берите ближайший к РФ из списка (Frankfurt/EU,
   если есть в списке на момент создания)
3. Подождите пару минут, пока проект поднимется
4. **Project Settings → Database → Connection string → Transaction pooler**
   (порт **6543** — экономит соединения, это то, что нужно обычному веб-бэкенду,
   не путать с Session pooler на 5432)
5. Скопируйте строку вида:
   ```
   postgresql://postgres.xxxxxxxx:ВАШ_ПАРОЛЬ@aws-0-eu-central-1.pooler.supabase.com:6543/postgres
   ```
   Это и есть `DATABASE_URL`.

### Проверка локально (необязательно, но полезно перед деплоем)

```bash
cp .env.example .env
# впишите DATABASE_URL из шага выше, смените JWT_SECRET
npm install
npm run dev
```

Если в консоли `✅ Сервер запущен` и `curl http://localhost:4000/api/health`
отвечает — база подключена правильно.

## Шаг 2 — деплой бэкенда на Render

Render по-прежнему деплоит только из Git-репозитория (GitHub/GitLab/Bitbucket).

### Подготовка репозитория

```bash
cd backend
git init
git add .
git commit -m "Backend Вместе на Postgres, готов к деплою"
git remote add origin https://github.com/ВАШ_ЛОГИН/vmeste-backend.git
git branch -M main
git push -u origin main
```

(если репозиторий уже есть — просто закоммитьте и запушьте изменённые файлы)

### Через Blueprint (проще всего)

1. render.com → **New +** → **Blueprint** → указать репозиторий → **Apply**
2. Render найдёт `render.yaml`, создаст сервис, сам сгенерирует `JWT_SECRET`
3. Единственное, что нужно вписать руками: **Environment → DATABASE_URL** —
   вставьте строку из Supabase (шаг 1)

### Вручную через дашборд (если Blueprint не подхватился)

1. **New +** → **Web Service** → подключите репозиторий
2. **Runtime**: Node, **Region**: Frankfurt, **Build**: `npm install`,
   **Start**: `npm start`, **Instance Type**: Free
3. **Environment Variables**:
   - `DATABASE_URL` = строка подключения из Supabase
   - `JWT_SECRET` = сгенерируйте: `node -e "console.log(require('crypto').randomBytes(48).toString('hex'))"`
   - `CORS_ORIGIN` = `*` (пока фронтенд не задеплоен; потом сузьте до его домена)
4. **Health Check Path**: `/api/health`
5. **Create Web Service**

### Проверка

```bash
curl https://vmeste-backend.onrender.com/api/health
```

Первый запрос после сна может идти до ~минуты — это нормально для free-тарифа
(это по-прежнему так: спит именно **сервер** на Render, а не база — данные
в Supabase это не затрагивает).

## Если карта в Northflank всё-таки пройдёт

Этот же бэкенд один в один деплоится и туда — ничего в коде менять не нужно,
только связать с тем же (или другим) Postgres:

1. Push тот же репозиторий на GitHub (уже сделано в шаге 2)
2. Northflank → New Service → Import from Git → выбрать репозиторий
3. Build: `npm install`, Start: `npm start`
4. Environment: тот же `DATABASE_URL` (Supabase) + `JWT_SECRET` + `CORS_ORIGIN`
5. Либо используйте бесплатную базу самого Northflank вместо Supabase —
   тогда просто возьмите её connection string вместо supabase-строки, код
   не отличит одно от другого, это всё равно Postgres.

## VPS (Timeweb Cloud / Selectel) — про запас, если понадобится

Всё из прошлой версии этого файла по-прежнему актуально и лежит в `deploy/`:
`setup-vps.sh` (ставит Node, nginx, certbot, pm2), `ecosystem.config.cjs`,
`nginx-vmeste-backend.conf`. Разница только одна: в `.env` на сервере тоже
нужен `DATABASE_URL` — можно тот же Supabase (тогда VPS вообще не нужен для
базы, только гоняет сам Express-процесс), либо поднять Postgres прямо на VPS
(`apt install postgresql`), если хочется, чтобы и сервер, и база были
целиком под вашим контролем.

```bash
ssh root@IP_VPS
cd /opt/vmeste-backend
chmod +x deploy/setup-vps.sh
sudo ./deploy/setup-vps.sh
# после -- впишите DATABASE_URL в .env на сервере, если скрипт сам не спросил
pm2 restart vmeste-backend
```

## Переменные окружения — сводка

| Переменная     | Обязательна | Назначение                                   |
|----------------|-------------|-----------------------------------------------|
| `PORT`         | нет (Render сам задаёт) | порт HTTP-сервера, по умолчанию 4000 |
| `DATABASE_URL` | **да**      | строка подключения к Postgres (Supabase и т.п.) — без неё сервер не стартует |
| `JWT_SECRET`   | **да, для прода** | подпись токенов; без неё — небезопасный дефолт |
| `CORS_ORIGIN`  | нет         | домен(ы) фронтенда через запятую; `*` — открыто всем |
| `PGSSL`        | нет         | `false` — отключить TLS (только локальный Postgres без TLS) |
| `PGSSL_STRICT` | нет         | `true` — строгая проверка сертификата (обычно не нужно для Supabase) |

## Что изменилось в коде при переходе на Postgres (коротко)

- `src/db/*` переписаны на `pg` (пул соединений, `queryOne/queryAll/execute`,
  транзакции через один и тот же клиент — это важно для атомарности).
- `schema.sql` — Postgres-диалект (`SERIAL` вместо `AUTOINCREMENT`, `now()`
  вместо `datetime('now')`); даты и время дат-полей (`created_at`,
  `resolved_at`) теперь приходят в JSON в формате ISO 8601
  (`2026-07-25T22:08:19.947Z`) вместо старого SQLite-формата — если фронтенд
  когда-нибудь будет парсить эти поля вручную, это стоит иметь в виду.
  `used_date`/`usage_date` остались обычным текстом `YYYY-MM-DD`, как и раньше.
- Добавлен `src/db/reset.js` (`npm run reset`) — только для разработки и
  тестов, полностью очищает таблицы и сбрасывает ID; замена старому
  `rm -rf data`.
- `package.json`: `engines.node` ослаблен до `>=18.0.0` — Postgres не требует
  той версии Node, которая раньше была нужна ради `node:sqlite`.

Все 9 файлов роутов и `test.sh` прогнаны заново на реальном локальном
Postgres — включая сценарий «чистая база с нуля» (то, что будет происходить
при первом деплое на настоящий Supabase).

## Юридический момент (не юридическая консультация)

Данные семьи теперь физически лежат на серверах Supabase (обычно US/EU,
в зависимости от выбранного при создании проекта региона) — та же ситуация,
что была бы и с Render. Если это когда-нибудь перерастёт в сервис с реальными
российскими пользователями — по 152-ФЗ их персональные данные должны сначала
собираться и храниться на серверах в России, так что стоит свериться с
юристом, а не только со мной. Для личного/пилотного проекта это обычно не
критично.

## Что ещё стоит сделать перед реальным использованием (необязательно сейчас)

- Rate limiting на `/api/auth/login` — `express-rate-limit` ставится за
  10 минут.
- Email не отправляется (подтверждение регистрации, восстановление пароля).
- У ребёнка обычный email+пароль вместо PIN/привязки к родителю.
